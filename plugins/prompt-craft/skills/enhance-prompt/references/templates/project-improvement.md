# 项目优化

只取本次有关的字段，复用已有信息，不要求逐项填满。“优化”没有明确对象时，先确认真正的痛点，不默认全仓重构。

## 补漏字段

- 目标与痛点：要改善哪个使用场景或维护问题？为何需要改变？
- 当前基线：已有行为、耗时、资源消耗或操作体验；选择与痛点有关且能获取的证据。
- 允许范围：只分析、给方案还是实施？哪些行为必须保留，哪些位置允许改动？
- 约束：沿用已有项目约定和用户限制；不自行指定技术栈、重构方向或性能数值。
- 前后验证：用可比较的场景检查目标是否改善、相关行为是否保留；未执行就不写成已证明。
- 交付：按原请求给诊断、方案或改动，说明依据、代价和未验证项。

## 整理方式

按“目标痛点 → 当前证据 → 瓶颈或原因 → 范围内方案 → 前后验证”组织请求。证据调查在执行阶段完成，不让增强阶段重复做完整诊断。

## 示例

原始想法：订单列表打开很慢，先查瓶颈、给优化建议，别改代码。

增强结果：分析订单列表打开缓慢的原因并给出优化建议，只分析、不改代码。先检查相关加载路径，用可获取的运行或代码证据说明当前情况，区分已确认瓶颈与待验证假设。围绕该问题提出建议，说明依据、取舍及后续如何比较优化前后的表现；没有运行验证的结论明确标注。
